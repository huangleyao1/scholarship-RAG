# 踩坑与优化笔记

## 1. 检索失败的常见根因之一是：块太大稀释语义

**问题**：附录粘在第十八条后，导致"六级/记过"等查询虽然检索到了对应块，但答案被块内其余信息淹没，排名上不去。
**调整**：下刀位置落在（一）（二）小节标题上，把块切小。
**教训**：检索质量问题优先检查切块（切块大小、语义绑定是否断裂）。embedding 模型对长文本的表征能力有限，一个块只讲一件事。

## 2. Chroma 向量库 add 是追加语义，不能直接覆盖

**问题**：重新跑 embed.py 往同名 collection 里 add，旧向量不会被替换，出现"新旧数据混在一起"。
**调整**：重建库必须先 `client.delete_collection(name)` 再 `get_or_create_collection()`；markdown 文本文件则直接覆盖写即可。
**教训**：破坏性操作前先备份。本项目已将干净语料从库中导出为 `data/chunks/chunks_clean.jsonl`，任何时候都能凭它重建向量库。

## 3. 查询稀释（query dilution）

**问题**：接入 LLM 初期，短问题回答良好，长问题回答经常偏离重点。【原因】：长问题中关键词被其他词语稀释——向量检索对整句做编码，长句中大量非核心词汇拉低了与目标块的相似度。
**调整**：让 LLM 把长问题改写成 2-3 个短检索词组，每个词组单独检索，结果按块文本去重后合并（上限8块，防上下文爆炸）。
**结果**：LLM 对复杂长问题的回答效果显著提升。

## 4. 检索质量分层排查：Top-3 条款级命中率 40% → 80%

**现象**：初版检索 Top-3 条款级命中率仅 40%（30条评测集，含直接问/同义改写/跨条款综合三类）。
**归因**（用独立参考实现 eval_lab 做交叉验证，逐层定位）：
- **(1) 评测协议失配（代码bug，非检索问题）**：eval.py 旧版不识别 gt 中的分号多候选标注，把"第十二条;各类荣誉获奖附加分"整体当作条款号做子串匹配，导致11条多候选题被结构性误判为 miss。
- **(2) 语料冗余（数据问题）**：学校《考评办法》与学院《实施细则》内容大量重叠（34/75 块，占45%），同一问题被两个文件的相似条款瓜分 Top-K 名次。eval_lab 对照实验：不排除上位文件时命中 66.7%（20/30），剔除上位文件后 80%（24/30）。
- **(3) 检索引擎参数（基础设施问题）**：修复 (1) 并重测仍只有 46.7%，且 multi 组一道未多中——定位到 Chroma HNSW 默认 `ef=10`，近似搜索在小向量库（41块）上严重失真，正确块根本没进入候选集。eval_lab（numpy 精确余弦，同一批数据）可到 80%，证实向量本身无问题。
**调整**
- eval.py 按分号拆分多候选 gt，命中任一即算对；
- 剔除上位文件，余弦空间重建库（统一模型版本 + 向量归一化）；
- 查询侧显式传 `hnsw_ef=500`（远大于库规模，近似搜索退化为精确检索），rag.py 生产路径同步修复。
**结果**：Top-3 条款级命中率 40% → 80%（30条评测集，direct/paraphrase/multi 三组均衡80%），eval.py 与独立参考实现 eval_lab 结果收敛，互相印证。
**方法论**：评测数据与判定逻辑是"协议"，两侧必须同步演进；排障时用独立参考实现做交叉验证，把"数据问题 / 代码问题 / 基础设施问题"分开归因，避免对着一个 bug 修另一个 bug。
